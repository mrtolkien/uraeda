# Rulings: Vim in text edit mode

The low-impact choices made while planning and building [the plan](plan.md), inside the limits of
[the spec](spec.md) and the decisions. None binds future work: those are decisions.

## R1: A buffer's edits are recorded beside the checkout they changed

- **Decision**: a buffer's save records the path it wrote in a file of that checkout's own git
  directory. The Commit page lists a recorded path as one `- Edit <path>` line, and a feature's pane
  lists only recorded paths.
- **Rationale**: the spec's scenario lists "Edit specs/PRIORITIES.md" for a line added by a buffer,
  where the structured diff would read "Add to Now". A feature's worktree also holds an agent's
  uncommitted work, which a pane must not offer to commit.
- **Alternatives considered**: every uncommitted file of a worktree, which offers an agent's work;
  the structured lines only, which contradict the scenario.
- **If wrong**: a lost record turns the lines back into today's structured ones; a feature's buffer
  edit then waits off the Commit page until recorded again.
- **Where**: tasks 2 and 7

## R2: A feature's files at any depth are written on its branch

- **Decision**: a buffer path under `specs/<folder>/` or `specs/changes/<folder>/`, at any depth, is
  written on that feature's or change's branch; every other Markdown file under `specs/` on the
  default branch, a merged feature's too, as it has no branch left (added while building task 2).
- **Rationale**: "any Markdown file under `specs/`" includes a feature's `contracts/`; its branch is
  where the feature's files live.
- **Where**: task 2

## R3: Discarding a pane restores the files a buffer edited

- **Decision**: a pane's Discard restores every file it lists, a buffer's edits included, after the
  confirmation that names them.
- **Rationale**: the pane lists what its commit holds, and its Discard drops what it lists; today's
  Discard keeps a proposal's typed text because the page never listed it as a line.
- **Where**: task 7

## R4: The mode store is outside React

- **Decision**: the focused field's mode and cursor live in a small external store read with
  `useSyncExternalStore`.
- **Rationale**: every keystroke moves the cursor; a context would re-render the shell each time,
  against the 16 ms keystroke target.
- **Where**: task 3

## R5: The settings tests run by their binary

- **Decision**: task 1's failing run is `cargo nextest run -p uraeda-core --test settings`, and the
  fate client is regenerated by the web's build, whose fate plugin writes it.
- **Rationale**: the plan's filter `settings` matches test names, not the file, and ran one test;
  the server has no script of its own that writes the client.
- **Where**: task 1

## R6: A several-lines field keeps its height, scrolling past it

- **Decision**: the `lines` variant is `rows` lines tall, scrolling inside past them, as the Astryx
  text area was; only the `line` variant grows with its text, to 9 lines.
- **Rationale**: `mockups/fields.html` draws a comment that "keeps its 7 rows, scrolling past them,
  as today", where the plan's interface said `rows` was a minimum height.
- **Alternatives considered**: a minimum height growing with the text, which moves the page under a
  long comment as it is typed.
- **If wrong**: `sizeTheme` in `fields/editor/theme.ts` sets `minHeight` in place of `height`.
- **Where**: task 3

## R7: A field's own keys are props of the editor, and one-line fields are `TextLine`

- **Decision**: the editor takes a field's own keys as `keys`, CodeMirror key names bound in its
  keymap before CodeMirror's own, each running the latest props' `run`: a row's Tab, Shift+Tab, and
  Backspace in an empty new row, a filter's Down and Up. It takes `onBlur`, which a row saves on.
  The one-line fields are `fields/TextLine.tsx`, the `line` editor under Astryx's `Field`, which
  draws the label, the help, and an error as `TextInput` did. A search's magnifier icon
  (`startIcon`) is left out: the placeholder says "Search".
- **Rationale**: the plan asks for a row's Tab "through the editor's keymap, not a listener of its
  own"; a keymap per caller would be a listener per file on the structural test's list.
- **Alternatives considered**: an `extensions` prop, which lets a caller add any listener unseen by
  the structural test; an icon drawn inside the editor's frame, a layout of its own for two fields.
- **If wrong**: a field's key moves back to a `keymap.of` of its own file, on the allowlist.
- **Where**: task 4

## R8: The composer is the editor's third variant

- **Decision**: the composer's editor is `variant: "composer"` with `rows` and a new `maxRows`: it
  grows from `rows` to `maxRows` lines, then scrolls inside, and has no frame of its own, since the
  composer's box is its frame. Folding slides its height over 150 ms, none with reduced motion.
- **Rationale**: the plan's interface said `variant: "lines"`, which R6 made a fixed height; the
  spec's architecture names three variants, the composer one of them. The editor's own frame inside
  the composer's box drew two frames.
- **Alternatives considered**: `lines` with a `maxRows` that makes it grow, which mixes R6's fixed
  height with the composer's growth in one variant.
- **If wrong**: `sizeTheme` in `fields/editor/theme.ts` folds `composer` into `lines`.
- **Where**: task 5

## R9: The page's drop target hears a drop first

- **Decision**: `attach/useImageDrop.ts` listens to drag and drop on the window in the capture
  phase, and hands every dropped file to the page's target, with no "a field took it already".
- **Rationale**: CodeMirror reads a file dropped on an editor as text and cancels the drop, so the
  page's target skipped it as handled: an image dropped on the composer's field, or any field taking
  images, was lost. The composer's Astryx input was the one field that took drops itself, and it is
  gone.
- **If wrong**: the editor takes a `drop` handler of its own that hands its files to the page's
  target.
- **Where**: task 5

## R10: The Vim layer's tests run on comments, not on priority rows

- **Decision**: `vim.test.tsx` checks insert mode at focus and Escape in normal mode on a round's
  comment field, which is on the editor already, in place of the priority row of US2 1 and 2. Escape
  in normal mode runs the field's own Escape action, a comment's leaving it and a row's asking
  "Discard your changes?", so the row's question follows from task 4's `onEscape`.
- **Rationale**: task 4 moves the rows to the editor in parallel with task 6; a test on a row would
  fail until both land.
- **If wrong**: once task 4 lands, a row of `vim.test.tsx` on the priority "Review the UI guidelines
  properly" can press `dw` then Escape and wait for "Discard your changes?".
- **Where**: task 6

## R11: Only the suggested message amends

- **Decision**: a pane's commit with the core's suggested message may amend the latest `chore:`
  commit of the lists, as the commit bar did; a message the human rewrote is always a commit of its
  own, as typed. A feature's pane commits its files alone (`git commit --only`), never amending.
- **Rationale**: an amend merges the subjects into a list, which would drop the message as typed
  (US6 3); the suggestion keeps today's run of small edits in one commit.
- **If wrong**: `changes::commit_pane` passes `amends: false` always.
- **Where**: task 7
