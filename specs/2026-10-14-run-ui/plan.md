# Plan: Run the UI easily

**Goal:** `npx uraeda` runs the web UI from npm on the user's Node 24, hands a second repository to
a server already running, and a version tag publishes the five npm packages from CI.

**Architecture:** the server's behaviour stays as it is; its start changes, and a package is built
around it ([spec, Architecture](spec.md#architecture)). Ownership:

- **Paths**: `packages/server/src/paths.ts` is the one home of where the server finds its plugin,
  its web UI, and its checkout. It returns the checkout's layout from the sources, and the package's
  from the bundle, which its build marks with the constant `URAEDA_PACKAGE`. `runner/claude.ts`,
  `binding.ts`, `env.ts`, `main.ts`, `dev.ts`, the dev scripts, and the web package's Vite config
  take their paths from it.
- **Settings**: `env.ts` owns the variables and the checkout's `.env`; `options.ts` owns the flags,
  which win over both. The package's layout has no checkout, so no `.env` is read.
- **The port**: `main.ts` owns it. It binds the port before anything opens the session cache, and
  releases it only by exiting. With the port bound, it starts the server and attaches the app to the
  listening HTTP server; with the port busy, it asks the server there, through `open-client.ts`, and
  exits.
- **Adding a repository at start**: one function, `openFolder` in `open.ts`, used by the server's
  own start and by the route `POST /open`. The list stays owned by the core, through the binding.
- **The browser**: `browser.ts`, called by `main.ts` only.
- **The version**: the binding's `version()`, from the Cargo workspace. The npm packages' committed
  versions are `0.0.0`; the release writes the tag's version.
- **The package**: `packages/uraeda/` builds `uraeda` from the other packages' outputs, and owns the
  smoke test. The release workflow, `.github/workflows/npm.yml`, owns publishing.

**Spec:** [spec.md](spec.md): the plan argues from the spec, so the implementer reads both.

## Review focus

The most consequential conditions or sequences the spec implies but does not name, including
interactions with existing behaviour. Each gets a test in the task that owns the code.

1. **A second start while the first one is still starting.** The first process holds the port before
   its server is ready. Requests that arrive then wait for the app instead of hanging, so a handoff
   within the 2 second timeout succeeds once the first is ready. Task 6.
2. **The running server is `vp dev`**, whose port is Vite's: `POST /open` must reach the server's
   handler, not Vite's fallback page. Task 5.
3. **A relative `--repo`** is resolved against the second process's folder before it is sent, so the
   running server, started elsewhere, adds the right folder. Task 6.
4. **A handoff never touches the session cache or the list in the second process**: it only sends
   the request. The running server's turns in progress stay in progress. Task 6.
5. **The smoke test leaves no server running**, whatever check fails: it ends the child it started
   on every path. Task 7.
6. **The bundle resolves `uraeda-binding` to the loader next to it**, never to the checkout's
   package: the smoke test runs from a folder outside the repository. Task 7.
7. **The release never regenerates the committed loader or declarations**: binaries are built
   without the JS binding, and the workflow fails if `packages/binding/index.js` or `index.d.ts`
   changed. Task 9.

## Task 9: The release workflow

**Files:**

- Create: `.github/workflows/npm.yml`

- Create: `packages/uraeda/scripts/release.test.ts`
- Modify: `packages/uraeda/scripts/smoke.ts` (reads the Cargo version through `release.ts`)

**Interfaces:**

- Consumes: `version()` (Task 1); `scripts/smoke.ts` and the build (Task 7); the `npm/` folders
  (Task 8).
- Produces: `node packages/uraeda/scripts/release.ts prepare <tag>` and `... publish <tag>`.
  `prepare` checks the tag without its `v` equals the Cargo workspace's version, which `version()`
  returns, read from `Cargo.toml` as the smoke test does
  ([R12](rulings.md#r12-the-release-reads-the-version-from-cargotoml)), writes it into the five
  `package.json` files with `npm pkg set` (and `napi version` for the `npm/` folders), sets
  `uraeda`'s `optionalDependencies` to the four names at exactly that version, checks the four
  `.node` files are in their folders, and prints each package's size. `publish` publishes each
  platform package not on npm at that version (`npm view <name>@<version>` answers 404), then
  `uraeda` the same way, with `npm publish --provenance --access public`, and `--tag next` when the
  version has a prerelease suffix. npm runs in each package's folder: in the checkout's root, the
  root's `devEngines` asking for pnpm makes npm refuse to run.

- [x] **Step 3: Implement `release.ts` and the workflow**

`npm.yml` runs on `push` of tags matching `release.yml`'s pattern, on `workflow_dispatch` with a tag
input (to complete a partial release), and on `pull_request` with `paths` on `packages/uraeda/**`,
`packages/binding/npm/**`, and `.github/workflows/npm.yml`. Jobs:

1. **binaries**, a matrix: `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` on
   `ubuntu-latest` with `--use-napi-cross`; `x86_64-apple-darwin` and `aarch64-apple-darwin` on
   `macos-latest`. Each installs Node 24 and pnpm 12.9.1 as `devEngines` pins them, runs
   `pnpm install --frozen-lockfile --ignore-scripts`, `rustup target add <target>`, then
   `napi build --platform --release --no-js --target <target>` in `packages/binding`, with
   `--use-napi-cross` on Linux, and `--output-dir ../../target/napi`
   ([R13](rulings.md#r13-the-release-builds-the-binaries-outside-the-package)). On Linux,
   `objdump -T` of the `.node` shows no `GLIBC_` above `2.17` (SC-003), with the target's `objdump`
   from the toolchain `--use-napi-cross` downloads
   ([R14](rulings.md#r14-the-glibc-check-uses-the-cross-toolchains-objdump)). It fails if
   `packages/binding/index.js` or `index.d.ts` changed. Uploads the `.node`.
2. **package**, on `ubuntu-latest`: builds the binding for the host, the web UI, and `uraeda`;
   uploads `packages/uraeda` with its built files.
3. **smoke**, a matrix on `ubuntu-latest` (linux-x64-gnu) and `macos-latest` (darwin-arm64), after
   both: downloads the package and the four `.node` files, which `napi artifacts` needs
   ([R15](rulings.md#r15-the-smoke-jobs-take-the-four-binaries)), runs it into the `npm/` folders,
   packs that platform package, and runs `smoke.ts --platform <its tarball>`.
4. **publish**, only on a tag or `workflow_dispatch`, after **smoke**, with
   `permissions: id-token: write, contents: read`: downloads everything, runs `napi artifacts`,
   `release.ts prepare <tag>`, then `release.ts publish <tag>`. No `NODE_AUTH_TOKEN` or npm token.

Format the workflow with `vp check`; it is not generated, unlike `release.yml`.
