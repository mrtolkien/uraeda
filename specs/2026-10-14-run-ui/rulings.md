# Rulings: Run the UI easily

The low-impact choices made while planning and building [the plan](plan.md), inside the limits of
[the spec](spec.md) and the decisions. None binds future work: those are decisions.

## R1: `--allowed-hosts` replaces the variable's list

- **Decision**: `--allowed-hosts a,b` sets the same list as `URAEDA_ALLOWED_HOSTS`, and replaces it
  when given, as `--port` replaces `URAEDA_PORT`.
- **Rationale**: the spec review asked for a flag ([spec-review.md](spec-review.md)). The
  [stack](../decisions/stack.md) decision names the hosts "listed in `URAEDA_ALLOWED_HOSTS`"; a flag
  for the same setting keeps one list and one guard, the way every other setting has a variable and
  a flag.
- **Alternatives considered**: merging the flag's names with the variable's: two sources to read to
  know what the server accepts.
- **If wrong**: a one-line change in `parseOptions`.
- **Where**: Task 3.

## R2: The bundle marks itself with a build constant

- **Decision**: the package's `vp pack` defines `URAEDA_PACKAGE`, which `paths.ts` reads to pick the
  package's layout.
- **Rationale**: the layout must not depend on where the files happen to sit, and the constant costs
  one `define`.
- **Alternatives considered**: guessing the layout from the folder names around the module, which
  breaks when the bundle moves; an environment variable set by a launcher, which a user could set by
  mistake.
- **If wrong**: the paths module changes alone.
- **Where**: Tasks 2 and 7.

## R3: The handoff goes through the running server, not the list

- **Decision**: the second start sends `POST /open` and never writes `repositories.json` itself.
- **Rationale**: the running server may use another data folder, and it must serve the page at once:
  the route adds and reloads its hosts before answering. The second process never opens the session
  cache, which keeps the running server's turns safe.
- **Alternatives considered**: writing the list through the binding, as `ura add` does, then opening
  the page: a race with the server's watch, and the wrong list when the data folders differ.
- **If wrong**: `handOff` changes alone.
- **Where**: Tasks 5 and 6.

## R4: The smoke test is a script, not a Vitest test

- **Decision**: `packages/uraeda/scripts/smoke.ts`, run by `vp run ready` and the release workflow.
- **Rationale**: it must run the packed package from a folder outside the repository, with a
  platform package in the release, which a test inside the server's Vitest project cannot do.
- **Alternatives considered**: a Vitest project for the package: the same work, with Vitest's module
  resolution between the test and the package.
- **If wrong**: the script's checks move into a test file.
- **Where**: Task 7.

## R5: Publishing in its own workflow

- **Decision**: `.github/workflows/npm.yml`, next to cargo-dist's `release.yml`, on the same tags.
- **Rationale**: `release.yml` is generated by `dist generate`, which would overwrite added steps.
- **Alternatives considered**: cargo-dist's own npm installer, which ships only the Rust binary.
- **If wrong**: the jobs move to another file.
- **Where**: Task 9.

## R6: The binding's default data folder is passed to `loadDataDir`

- **Decision**: `loadDataDir(root, core, environment?)` takes the binding's `dataDir` from its
  caller, and `env.ts` no longer imports `uraeda-binding`.
- **Rationale**: `env.ts` imported the binding at the module's top, so `main.ts` loaded it before
  parsing its options: `--help` failed without a built or installed binding, and a missing binding's
  error escaped the `uraeda: ` prefix. With the binding passed in, `main.ts` loads it only through
  `loadBinding()`, after `--help`, inside its error handling.
- **Alternatives considered**: importing `env.ts` dynamically in `main.ts`: `parseOptions` needs
  `loadEnv` before `--help` is known; loading the binding lazily inside `env.ts`: a synchronous
  `loadDataDir` cannot await an import.
- **If wrong**: `loadDataDir` imports the binding again, and `--help` loads it.
- **Where**: Task 3.

## R7: `vp run ready` builds the web UI before the tests

- **Decision**: in `ready`, `vp run --filter uraeda-web build` moves from the end to just before
  `vp test`.
- **Rationale**: the start now fails without `packages/web/dist/index.html`, as the spec requires,
  and `main.test.ts` starts the server; in CI the UI was built only after the tests, so every start
  in them would fail with the "not built" message.
- **Alternatives considered**: keeping `--web-root` for the tests, which the spec removes; writing a
  placeholder `index.html` into `packages/web/dist` from the tests, which a later `pnpm start` would
  serve as the UI.
- **If wrong**: the tests start the server with another way to name the web folder.
- **Where**: Task 3.

## R8: A list the running server cannot change answers 400

- **Decision**: `POST /open` answers 400 with the core's message, without `refused: `, when adding
  the repository fails, as it does for a given folder outside git.
- **Rationale**: the spec names only the folder outside git; a 400's `error` is printed by the
  second start, which exits 1, so the human reads why the running server could not open the
  repository instead of the "used by another program" message.
- **Alternatives considered**: 500, which the second start treats as another program on the port.
- **If wrong**: the route's `catch` changes alone.
- **Where**: Task 5.

## R9: `--binding` takes a folder

- **Decision**: the smoke test's `--binding` takes a `.node` file, or a folder holding exactly one
  `uraeda-binding.*.node`; `vp run ready` passes `--binding packages/binding`.
- **Rationale**: the plan finds the checkout's `.node` by its name, and `vp run` runs a script's
  simple commands without a shell, so `packages/binding/uraeda-binding.*.node` reaches the script
  unexpanded. A folder finds it on any platform.
- **Alternatives considered**: a shell glob, which `vp run` does not expand; naming the Linux x64
  file, which breaks `vp run ready` on macOS.
- **If wrong**: `nodeFile` in the smoke test changes alone.
- **Where**: Task 7.

## R10: The smoke test expects the Cargo version before a release

- **Decision**: the version check expects the installed package's version, or, while it is `0.0.0`,
  the Cargo workspace's version from the checkout's `Cargo.toml`.
- **Rationale**: `uraeda --version` prints the binding's `version()`, the Cargo workspace's, so a
  checkout's build prints `0.4.0` while the committed package says `0.0.0`. The release writes the
  tag's version into the package, and then both must agree.
- **Alternatives considered**: expecting `0.0.0`, which the command never prints; accepting any
  version, which would not catch a binding of another release.
- **If wrong**: `expectedVersion` in the smoke test changes alone.
- **Where**: Task 7.
