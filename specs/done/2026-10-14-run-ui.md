# Record: Run the UI easily

> [!NOTE]
>
> The record of a merged feature, not instructions to follow. Started on 2026-10-14, finished on
> 2026-10-15, in [its pull request](https://github.com/mrtolkien/uraeda/pull/17). Its full files are
> in git: `git log -- specs/2026-10-14-run-ui/`.

## What and why

The web UI only ran from a checkout of Uraeda, with Rust, Node, pnpm, and a build. The human asked
for the best and simplest way to package Uraeda today, so anyone can run it with one command, and
for every promising solution to be tested: a single binary, a desktop app, or `npx uraeda`. Three
were built and run during discovery: an npm package (3.5 MB, needs Node 24), a Node single
executable (159 MB), and a Bun one (90 MB). The human chose the npm package.

## Behaviour

- `npx @uraeda/ui` in a repository starts the server on 127.0.0.1:4310, adds the repository's main
  checkout to the list, prints `Uraeda server on http://127.0.0.1:4310`, and opens `/r/<name>/` in
  the browser. Outside git it prints
  `uraeda: <folder> is not in a git repository: add one from the web UI` and opens `/`, where the
  most recent repository opens. It needs Node 24 or later; sessions still need `claude`.
- Options: `--port <port>` (`URAEDA_PORT`), `--repo <folder>` (`URAEDA_REPO`), resolved against the
  current folder, `--allowed-hosts <names>` (`URAEDA_ALLOWED_HOSTS`, comma separated, replaced by
  the flag when given), `--no-open`, `--version` (the Cargo workspace's version, from the binding),
  and `--help`, which prints the options. An unknown option exits 1 with
  `uraeda: unknown option --<name>; see uraeda --help`. `--allow-origin` stays, undocumented, for
  development servers.
- Started from the package, the server reads no `.env` file: settings come from flags and the
  environment only, so a cloned repository's `.env` cannot widen the host names the server accepts.
  A checkout's `vp dev` and `pnpm start` still read `.env` at the checkout's root.
- The command takes its port before anything opens the session cache. When the port is busy, it
  sends `POST /open` with `{ folder, given }` to the server there, within 2 seconds: an answer with
  a `uraeda` field adds the repository to that server's list, prints
  `Uraeda already runs at http://127.0.0.1:<port>/r/<name>/`, opens it, and exits 0; a 400 prints
  `uraeda: <error>` and exits 1, as for a given folder outside git; anything else prints
  `uraeda: port <port> is used by another program: pass --port to use another one` and exits 1.
  Requests that reach a server still starting wait for it. Before this feature, a second start on a
  busy port marked the running server's turns as stopped in the shared cache.
- `POST /open` sits behind the same `Host` and `Origin` guard as every route, answers 400 with
  `{ error }` for a body without an absolute folder, or when the core refuses to change the list,
  and reloads the hosts before answering, so the page is served at once. `vp dev` answers it too.
- The browser opens with `open` on macOS and `xdg-open` on Linux, detached, without waiting. It is
  not opened over SSH (`SSH_CONNECTION` or `SSH_TTY`), nor on Linux without `DISPLAY` or
  `WAYLAND_DISPLAY`. A failed launch prints `uraeda: could not open a browser: <reason>`, and the
  server keeps running.
- In the package, a missing platform binding prints the loader's own error, prefixed with
  `uraeda: `. In a checkout, a binding older than the Rust core, or not built, names the `vp run`
  command to build it; a web UI not built exits 1 with
  `uraeda: the web UI is not built; run vp run --filter uraeda-web build`.
- A version tag that releases `ura` also publishes, through `npm.yml`, the four platform packages
  then `@uraeda/ui`, at the Cargo workspace's version, with provenance and no npm token, once the
  four binaries are built and the smoke test passed on Linux x64 and macOS arm64. A prerelease goes
  to the `next` dist-tag. Running the workflow again on the same tag skips what npm already has. On
  a pull request that changes the package or the workflow, it runs up to the smoke test.

## Design

The server's behaviour is unchanged; its start changed, and a package was built around it, as the
[distribution](../decisions/distribution.md) decision says.

- [`paths.ts`](/packages/server/src/paths.ts) is the one home of where the server finds its plugin,
  its web UI, and its checkout: `layout()` returns the checkout's layout from the sources, and the
  package's from the bundle, which its build marks with the constant `URAEDA_PACKAGE`.
  `requireWeb()` checks the UI is built.
- [`options.ts`](/packages/server/src/options.ts) owns the flags and the help text;
  [`env.ts`](/packages/server/src/env.ts) the variables, and the checkout's `.env` only when there
  is a checkout.
- [`main.ts`](/packages/server/src/main.ts) owns the port: it binds it with `node:http`, then either
  starts the server and attaches the app to the listening server, queueing early requests, or hands
  the repository over through [`open-client.ts`](/packages/server/src/open-client.ts).
- [`open.ts`](/packages/server/src/open.ts) holds `openFolder`, the one way a folder is added at
  start, used by [`server.ts`](/packages/server/src/server.ts) and by the route `POST /open`.
- [`browser.ts`](/packages/server/src/browser.ts) opens the browser, without a dependency.
- [`binding.ts`](/packages/server/src/binding.ts) checks the binding's freshness only in a checkout;
  the binding's `version()` ([`lib.rs`](/crates/binding/src/lib.rs)) is the one home of the version
  the command prints and the release checks.
- [`packages/uraeda/`](/packages/uraeda/) is the npm package `@uraeda/ui`: `vp pack` bundles
  `main.ts` into one file, `dist/uraeda.mjs`, with `uraeda-binding` resolved to the napi-rs loader
  copied unchanged as `dist/binding.js`; [`build.ts`](/packages/uraeda/scripts/build.ts) copies the
  web UI and the plugin, following the skill's symlink.
  [`smoke.ts`](/packages/uraeda/scripts/smoke.ts) packs and installs it in a temporary folder
  outside the repository, then checks it as a user runs it; `vp run ready` runs it with the
  checkout's binding.
- [`packages/binding/npm/`](/packages/binding/npm/) holds the four platform packages, generated by
  `napi create-npm-dirs` from `napi.targets`, named `@uraeda/binding-<platform>` from
  `napi.packageName`, committed at version `0.0.0`.
- [`npm.yml`](/.github/workflows/npm.yml) builds the four binaries (Linux with napi-rs's cross
  toolchain, for a glibc 2.17 floor, the arm64 one's C code with clang; macOS on macOS runners),
  builds the package, runs the smoke test on Linux x64 and macOS arm64, then
  [`release.ts`](/packages/uraeda/scripts/release.ts) sets the versions and publishes, in the GitHub
  environment `npm`, which only version tags may deploy to.

## Questions

### Round 01

#### Q1: How does Uraeda ship?

**Answer:** A: an npm package, `uraeda`, run with `npx uraeda` on the user's Node 24, with the
binding in one package per platform. A single executable can come later behind the same command.

#### Q2: Does `ura` start the web UI?

**Answer:** A: they stay separate, `ura` from its installers and `npx uraeda` for the web UI, both
released with the same version from the same tag.

#### Q3: Which names does Uraeda take on npm?

**Answer:** A: `uraeda`, with the four platform packages named as the generated loader expects,
`uraeda-binding-<platform>`.

#### Q4: What happens when the port is already taken?

**Answer:** A: when the port answers as Uraeda, the current repository is added to it and opened,
and the command exits; when another program holds it, the command fails and names `--port`.

#### Q5: Does the command open the browser?

**Answer:** A: by default, with `--no-open` to skip it, and the URL always printed.

#### Q6: How are releases published to npm?

**Answer:** A: from CI on the version tag, with trusted publishing, after the human publishes each
package once by hand.

#### Q7: Which channels does this feature cover?

**Answer:** A, npm only: "We might do homebrew and nix later, but it's not crucial".

## Decisions

- [Distribution](../decisions/distribution.md): new; the npm package `@uraeda/ui` on the user's Node
  24, four platform packages, no install scripts, one module for the server's paths, no `.env` in
  the package, and releases published by CI from `ura`'s tag, platform packages first, behind a
  gate.

## Changes after approval

- The spec review asked for an `--allowed-hosts` flag, which replaces `URAEDA_ALLOWED_HOSTS` when
  given (R1), and called the package size limits of SC-001 not critical: sizes are printed, never a
  gate.
- In a checkout, `main.ts` reads `.env` and takes its default repository from the checkout's root,
  not the folder it was started in.
- A list the running server cannot change answers 400 with the core's reason (R8).
- `vp run ready` builds the web UI before the tests, which now need it (R7), and runs the package's
  smoke test after it.
- The publish job runs in the GitHub environment `npm`, on actions pinned to commit SHAs, and checks
  Node 24's own npm instead of installing one (R16), after the final review found a branch editing
  `npm.yml` could publish.
- The Linux arm64 binary's C code compiles with clang, as napi-rs's GCC 4.8.5 lacks the NEON
  intrinsics `libwebp-sys` uses (R17).
- Every package moved under the human's npm organization `@uraeda`: the web UI as `@uraeda/ui`, the
  platform packages as `@uraeda/binding-<platform>`, through the binding's `napi.packageName`. npm
  refused to publish `uraeda`, as too close to `ramda`. The command stays `uraeda`.

## Follow-ups

- `--port 0` starts on a random port but prints port 0, and the guard then refuses every request.
- A second start during the first's start times out after 2 seconds, and reports "another program",
  when the first waits longer on `claude --version`, whose own timeout is 5 seconds.
- The smoke test's `URAEDA_PORT=5000` line checks nothing, since `--port` is passed; its "missing
  binding" check runs only without `--binding` or `--platform`, which neither `vp run ready` nor the
  workflow does; the smoke script lives about 10 seconds longer than its checks, on a timer it never
  clears.
- No end-to-end test covers `URAEDA_PORT`, `--no-open` reaching the opener, or the start's exit on a
  missing web UI; they are unit-tested in `env.test.ts`, `browser.test.ts`, and `paths.test.ts`.
- The loader's error for a missing platform package points to an npm bug, not to the package to
  install.
- The platform list lives in `napi.targets`, `release.ts`, the workflow's matrices, and two tests;
  the Cargo version is read by two regular expressions; the "web UI is not built" text is in
  `build.ts` and `paths.ts`.
- `-x` reports `unknown option --x`, and `repositories.ts` still prefixes its messages with
  `uraeda-server: `.
- The `package` job rebuilds the loader without checking it is unchanged; the smoke test's loader
  check catches a difference.
- A Homebrew formula and a Nix package for the web UI, left for later (Q7).
- A single executable, once Node's single executable applications leave active development, or users
  ask to run Uraeda without Node: the distribution decision's revisit condition.
