# Record: Skill and web UI apart

> [!NOTE]
>
> The record of a merged change, not instructions to follow. Started on 2026-11-04, finished on
> 2026-11-04, in [its pull request](https://github.com/mrtolkien/uraeda/pull/96). Its full files are
> in git: `git log -- specs/changes/2026-11-04-skill-ref/`.

## What and why

The human asked for a clear line between the skill and its references, and the web UI: "The web ui
is its own thing. Don't mix both." The skill had grown lines only the web UI needs, its offer blocks
and cards, sessions moving between worktrees, its pages, and what it folds, draws, or shows live. An
agent in another harness read instructions it could not follow, and a reader could not tell the
workflow from one tool.

## Behaviour

- The skill, its templates, and its example describe the workflow for any harness, and never the web
  UI. A session on the main checkout offers a change in words, with its proposal, and an upgrade to
  a feature with its reason in one sentence; on the human's yes, the agent starts it with `ura` or
  by hand.
- Every session the web UI runs gets the web UI's own instructions, appended to its system prompt on
  every start, resumed ones included: offers as `uraeda-offer change` and `uraeda-offer feature`
  blocks, which it shows as cards; a spoken yes answered with the block again, since only the card
  moves a session into a change's worktree, or a change's sessions to a feature; the `/f/<folder>`
  page of a change another session makes; what it shows live of the agent's messages; paths from the
  repository root.
- What the web UI draws for the human, like decision icons, folded scenarios and edge cases, the
  "Data" section, story previews, the New page's starts, the inbox's buttons, and "Fix moved links",
  is described in [the web UI's page](/docs/app.md), in **The workflow's files** and **Sessions with
  Claude Code**.
- Setting up a project's preview keeps its requirements in the skill, said of "a tool that shows the
  preview" and of `uraeda-preview.js`, which stops a webpack Storybook. The preview decision's
  template and example keep naming Uraeda, as a project's decision names the tool it relies on.

## Design

The web UI's instructions live in [`instructions.ts`](/packages/server/src/runner/instructions.ts),
agent-neutral text, and the Claude adapter passes them with `--append-system-prompt` in
[`claudeArgs`](/packages/server/src/runner/claude.ts). The offer block's language, `OFFER_LANGUAGE`,
has its one home there, and the web UI's [`offers.ts`](/packages/web/src/offers.ts) imports it. A
second skill in the server's plugin folder was weighed and dropped: an agent loads a skill only when
its description matches, so an offer could go unmade.

Three tests keep the line: [`the_skill_never_describes_the_web_ui`](/crates/cli/tests/skill.rs)
fails when `SKILL.md`, a reference, a template, or an example file says "web UI", "uraeda-offer",
"in Uraeda", "Uraeda shows", or "Uraeda's helper";
[`claude.test.ts`](/packages/server/src/runner/__tests__/claude.test.ts) checks the instructions in
a new and a resumed session's arguments; and
[`offer-instructions.test.ts`](/packages/web/src/__tests__/offer-instructions.test.ts) reads the
instructions' example offer with the card's parser.

## Gotchas

- The instructions override the skill where the web UI differs, and say so: on a spoken yes, the
  skill starts the change, and the instructions offer the block again. Another agent's adapter must
  pass the same text its own way, or its sessions offer in words, which no card catches.
