# Record: CLI core features

> [!NOTE]
>
> The record of a merged feature, not instructions to follow. Started on 2026-10-10, finished on
> 2026-10-11, in [its pull request](https://github.com/mrtolkien/uraeda/pull/2). Its full files are
> in git: `git log -- specs/2026-10-10-cli-core/`.

## What and why

`ura` became the fast path through the workflow, for humans and agents: it shows where every feature
stands across branches, tells an agent its next step, validates the `specs/` folder, records answers
and reviews with their commits, drafts and starts features, sets a project up with a version-matched
skill, and ships as an installable binary. The human asked for a standard CLI plus keyboard-driven
ratatui screens, and for agents to go through the CLI, "less error prone than telling an agent what
it needs to do". The screens were split into the next feature; the commands came first, since the
gain for agents comes from them, and the skill keeps its manual instructions so the workflow still
works without `ura`.

## Behaviour

- `ura status`, from any branch, lists every started feature and bug, read from the default branch,
  each branch's tip, and the working tree, grouped by `PRIORITIES.md` section, with its next step,
  who it waits on (`you` or `agent`), and the waiting file's first line; unstarted entries show as
  `not started`, uncommitted edits (deleted files included) and `(behind origin by N)` are flagged,
  and merged remote branches are not listed. It never fetches, and says when the remotes were last
  fetched. `--json` gives the same data.
- `ura next [target]` gives the target and its step from the skill's tables: the feature, its
  branch, the step's name, the reference file, whether it waits on the human, and the first
  unchecked task; pull request states come from `gh`, else `unknown`. With nothing for an agent,
  `--json` prints `"feature": null` and a step object whose `name` is `"none"`, exit 0.
- `ura check [target]` validates every workflow file against the skill's rules: frontmatter values,
  sections read from the embedded templates (numbered headings in their full form, `Q1:`), answers
  (follow-ups that do not apply are not reported), the `[!IMPORTANT]` block of a file waiting for
  the human, and links to markdown files or into `specs/` with their headings. Each problem is
  `<file>:<line>: <message>`, exit 1; `--json` lists them. It runs in `vp run ready` on `specs/` and
  on the skill's example.
- `ura answer [target] <Qn|Qn.X|notes> "<text>"` writes one answer, or the human's notes, and
  commits nothing; `--submit` requires every applicable answer, sets `answered`, turns the
  `[!IMPORTANT]` block into its `Answered on` record, and commits
  `discovery(<slug>): answer round NN`. A submitted round takes no more answers, and an answer line
  cannot start with `#` or `**Answer:**`.
- `ura review [target]` adds comments with `--comment <lines> "<text>"` to `spec-review.md`,
  `plan-review.md`, or `assessment-review.md` (`verdict: pending`, the reviewed `commit`, each line
  comment quoting its lines under the nearest heading), then `--approve`, optionally with comments
  and `--risk-tier`, or `--request-changes`, which needs a comment. The status, the record block,
  and the review file are committed together, `spec(<slug>): approve`; an approval without comments
  deletes the old review file. A pending review of an older version is refused, and `--plan-review`
  only applies to a `medium` tier.
- Writing on a feature's branch, `answer` and `review` used its worktree when it had one, else
  switched the checkout to it when clean and stayed there, else refused naming the uncommitted
  files; the web UI feature replaced the switch with worktrees under `.worktrees/`. Commits run the
  user's hooks, with their identity, refuse when other files are staged, and `--no-commit` leaves
  the files written. `ura` never pushes.
- `ura init`, anywhere in a git repository, creates the missing parts of `specs/` at the top level
  (the four folders with a `.gitkeep`), never overwrites, and installs the embedded skill in
  `.agents/skills/uraeda/` with a SHA-256 manifest, linked from `.claude/skills/uraeda`. Running it
  again updates the skill files nobody edited and lists the others; `--no-skill` skips the skill.
  Nothing is committed.
- `ura draft <text>` finds the one `PRIORITIES.md` line matching the text, writes
  `specs/drafts/<slug>.md` from the proposal template with the line as title, turns the line into a
  link to it, and opens `$VISUAL`, `$EDITOR`, or `vi` (`--no-edit` skips it). No commit.
- `ura start <target>` starts a draft or a postponed folder, even uncommitted: on the default
  branch, the entry moves to the end of **Now** as a link to the future `proposal.md`, committed;
  then the new branch gets the draft moved unchanged as `proposal.md`, committed. It refuses a dirty
  tree, an existing branch or folder (`--slug` overrides the slug), and a draft still holding the
  template's placeholders. On a bug it stops with `unimplemented!`, exit 101, until the bug flow is
  specified. As merged it checked the new branch out; the web UI feature moved it to a worktree.
- The skill names each command at the step it serves and keeps every manual instruction. It gained
  the review files, approval comments carried out by the next step (the plan's `## Review comments`,
  or the implementation), the clarifications' **Notes:** field, and a manual start that leaves
  `proposal.md` uncommitted, with a human gate on it until committed.
- On each version tag, dist builds `ura` for Linux and macOS on x64 and arm64, with a shell
  installer and a Homebrew formula in `mrtolkien/homebrew-tap`; Nix users run it from the flake.
  `v0.1.0` was tagged after the merge.

Every command takes one optional target, resolved the same way: a path under `specs/`, or a name
matching exactly one item. Errors are one `ura: <message>` line on stderr and exit 1; a refused
action changes nothing; edits keep every other byte of a file, Windows line endings included.

## Design

The core reads the whole `specs/` folder into a `Workspace` model, from the default branch, every
feature branch's tip, and the working tree, with gix in process; it derives each feature's step from
the skill's tables, checks the files against the rules the skill and its templates state, and
performs the human actions, each checking every condition before writing anything. Writes go through
the system `git`, so hooks run. The CLI is a thin clap layer with text and versioned JSON output,
and the binding can expose the same model to the web UI.

- Git module, [`crates/core/src/git.rs`](/crates/core/src/git.rs): the only code that reaches git;
  gix, without default features but with `status`, for reads, `git` for commits and switches.
- Workflow file parsers, [`crates/core/src/files/`](/crates/core/src/files/), on pulldown-cmark with
  source offsets: frontmatter, headings, questions and answers, blocks, plan tasks, review comments,
  links.
- Workspace model, [`crates/core/src/workspace.rs`](/crates/core/src/workspace.rs), targets,
  [`crates/core/src/target.rs`](/crates/core/src/target.rs), and steps,
  [`crates/core/src/steps.rs`](/crates/core/src/steps.rs).
- Checks, [`crates/core/src/check/`](/crates/core/src/check/), one rule per function with a stable
  id, the section rules read from the templates embedded by
  [`crates/core/src/embedded.rs`](/crates/core/src/embedded.rs).
- Actions, [`crates/core/src/actions/`](/crates/core/src/actions/): answer, submit, comment,
  approve, request changes, draft, start, init. Dates come from `URA_TODAY`, else `date +%F`, in
  [`crates/core/src/today.rs`](/crates/core/src/today.rs).
- The CLI, [`crates/cli/src/`](/crates/cli/src/), one module per command, tested by running the
  built `ura` in temporary repositories with a hook that records its runs
  ([`crates/cli/tests/`](/crates/cli/tests/)), and broken files in
  [`fixtures/broken/`](/fixtures/broken/).
- Release: [`.github/workflows/release.yml`](/.github/workflows/release.yml), generated by dist,
  [`dist-workspace.toml`](/dist-workspace.toml), and [`flake.nix`](/flake.nix)'s package.
- The skill, [`skills/uraeda/`](/skills/uraeda/), with the review file's template.

## Questions

### Round 01

#### Q1: What does this feature deliver?

**Answer:** A: the core, every command in its non-interactive form, `ura init`, the review file
format, the skill's rewrite, and the release; the answer, review, and draft TUIs become the next
feature.

#### Q2: How does the skill send agents through the CLI?

**Answer:** A: the rules stay written in the skill, each step names its command, and `ura check`
verifies only rules the skill states.

#### Q3: Which commands come beyond the proposal's five?

**Answer:** B: only `ura check` and `ura next`, "we'll do `ura start` later"; the human then asked
for `ura start` in the spec's first review, and it shipped here.

#### Q4: What does `ura draft` create?

**Answer:** A, "simpler": a draft in `specs/drafts/` linked from its line, opened in the editor,
with no commit.

#### Q5: What does `ura status` show?

**Answer:** A: every feature and bug across the default branch, each branch's tip, and the working
tree, one line each, as a table or `--json`.

#### Q6: How does `ura` run git?

**Answer:** B: gix for reads, the system `git` for writes.

#### Q7: Where do `answer` and `review` write when the feature's branch is not checked out?

**Answer:** A: the branch's worktree, else a switch when the tree is clean, else a refusal; the web
UI feature later reversed the switch for worktrees under `.worktrees/`.

#### Q8: Do the commands commit your answers and reviews?

**Answer:** A: commit on submit with the human's identity, only the files changed, `--no-commit` to
opt out, and never push.

#### Q9: What can a review conclude?

**Answer:** A: approve with optional comments, carried out by the next step, or request changes with
at least one comment.

#### Q10: Where do review comments live?

**Answer:** A, a review file next to the reviewed one, but with no round number, "we can
override/remove the old one", and "only exists if there are comments".

#### Q11: How does a comment point to its place?

**Answer:** A: the line range at the reviewed version, the quoted lines, and the nearest heading.

#### Q12: What does `ura review` show, and what is the "active line"?

**Answer:** A: rendered markdown with a cursor on a block, commented on as its source lines; left to
the TUI feature.

#### Q13: How does typing start in `ura answer`?

**Answer:** A: lowercase letters are motions, uppercase letters, digits, and space start typing, `i`
or Enter start empty; left to the TUI feature.

#### Q14: What should the TUIs look like?

**Answer:** A: the terminal's own 16 colours, a LazyVim-shaped bottom bar, and rounded borders; left
to the TUI feature.

#### Q15: Does `ura init` install the skill?

**Answer:** A, the embedded skill in `.agents/skills/` and `.claude/skills/`, "but have CLI options
for B", which became `--no-skill`.

#### Q16: How do users install `ura`?

**Answer:** "C if it's not too much work and they can install the binary directly": dist's shell
installer, plus a Homebrew tap of the release binary and a Nix flake package.

#### Notes

"LGTM": the settled points were accepted, and the human asked for a **Notes** space in the
clarifications template for feedback on them, which this feature added.

## Decisions

- [Git](../decisions/git.md), new: Rust tools read git with gix and write with the system `git`,
  never bypassing hooks, through one module of the core.
- [CLI](../decisions/cli.md), new: the skill holds every rule and names each command, targets are
  resolved one way, every TUI action has flags, read commands have versioned JSON, and the skill is
  embedded in the binary.

## Changes after approval

- The size limit rose from 3 MB to 5 MB for gix's `status` feature, as the human accepted: spec
  revision 3 (ruling R1).
- The plan was approved without a review, at the human's request, despite the `high` tier (R2).
- Dates use `URA_TODAY`, else `date +%F`, else the UTC date (R3).
- `ura next --json` with nothing to do prints a step object named `none`, not a string (R4).
- `ura check` does not report an `[!IMPORTANT]` block left in an answered or approved file, which
  the next step turns into a record (R5).
- `ura check` checks only links to markdown files or into `specs/`, since specs link to code not yet
  written (R6).
- Commits stage `ura`'s files and refuse other staged files, so a reformatting hook leaves a clean
  tree (R7).
- dist 0.33, the version in nixpkgs, instead of 0.32; its `release.yml` runs its own plan on pull
  requests (R8).
- The TUIs' draft, [`cli-tuis.md`](../drafts/cli-tuis.md), is linked from the human's "Nice TUI"
  entry in **Later**, not a new **Now** entry (R9).
- On the pull request: a failed start commit stays on the default branch with what is left; a
  pending review of an older version is refused; `--plan-review` only with a `medium` tier; a
  submitted round takes no answer; a deleted file counts as uncommitted; numbered headings need
  their full form.

## Follow-ups

- Merged features are left out of the model, so `source: default-branch` is never produced, and a
  postponed feature whose remote branch was never deleted shows as waiting for its proposal (R10).
- A failing hook's error shows its first line only (R10).
- Checkboxes of a non-task section after a plan's last task count toward that task (R10).
- From the pull request's review, not taken: decision states are read from the feature branch's tip,
  not the default branch's current ones; numbered sections are not checked for their order.
- The answer, review, and draft TUIs, with Q4 and Q12 to Q14's answers, in
  [the draft](../drafts/cli-tuis.md).
- `ura start` on a bug, until the bug flow has its spec; `ura postpone`, `ura drop`, and a round
  scaffolding command.
