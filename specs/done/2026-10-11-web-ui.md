# Record: Web UI for the workflow files

> [!NOTE]
>
> The record of a merged feature, not instructions to follow. Started on 2026-10-11, finished on
> 2026-10-12, in [its pull request](https://github.com/mrtolkien/uraeda/pull/3). Its full files are
> in git: `git log -- specs/2026-10-11-web-ui/`.

## What and why

A web UI that shows every step of the workflow with a readable hierarchy, and performs the human
steps: drafts, proposals, answers to questions, and spec, plan, and assessment reviews. It is how
the human works on Uraeda, dogfooding, mostly from an iPhone over Tailscale, so it is built for the
phone first, and runs with `vp dev` at the root of the repository it shows. Files render with their
structure, not as plain markdown: each question a block with its options, pros, and cons, and a
comment field, like a coding agent's "clarify" tool. The stack was set by the human: React, Astryx,
and fate, on the Rust core.

## Behaviour

- Home lists, in groups left out when empty: what waits on the human, grouped by action; what agents
  are working on, with their step; the Now and Next lines of `PRIORITIES.md` not started yet, with
  "Draft" for a line without a draft and "Start" for one linking a draft; and features merged into
  the default branch, as Done, also in `ura status` with the source `default-branch` and the step
  `done`. A feature's page shows its waiting block, branch, worktree, files in workflow order with
  their status (missing ones "not yet"), and the problems `ura check` finds, only for a feature read
  from a working tree (ruling R2).
- A round of questions is one page: every question and every option in full, never folded, cut, or
  boxed; follow-ups inside their parent once their letter is picked; answers saved as typed,
  uncommitted, written as `A`, `B and C`, or `A, B and C`, then `: <comment>`, a comment alone as
  typed, `-` for "Does not apply"; a progress bar, the settled points, the notes, and Submit, which
  is refused while an applicable question is blank, saves what is shown first, and stops when it
  could not be saved.
- A review shows the version committed at the branch's tip, with stories, scenarios, and plan tasks
  structured but unboxed; tapping blocks (table rows included) selects lines to comment on; pending
  comments, the general one included, are written to the review file as added, editable and
  removable; the verdict offers, for a spec, the risk tier and plan review, and is refused when the
  file on disk differs from the tip; Request changes needs a comment.
- Drafts and proposals are edited in a plain text area, saved byte for byte as typed, previewed, and
  committed (`chore: draft <title>`, `chore(<slug>): proposal`, `chore(<slug>): edit the proposal`);
  "Start" runs `ura start` into a new worktree. Only plain paths under `specs/drafts/` or
  `specs/backlog/` are accepted as drafts.
- Every write, from the UI or from `ura answer`, `review`, `draft`, and `start`, lands on its branch
  without switching the checkout: in the checkout or worktree that has the branch, else in a new
  worktree at `.worktrees/<branch>/`, kept out of `git status` through `.git/info/exclude`, running
  the main checkout's hooks. `ura start --switch` keeps the old switching behaviour. Worktrees are
  never removed automatically.
- `vp dev` at the root serves the UI and the server in one process on `127.0.0.1:4310`; `.env`
  (git-ignored, from `.env.example`) sets `URAEDA_ALLOWED_HOSTS`, the tailnet's full host names
  accepted besides 127.0.0.1 and localhost, `URAEDA_PORT`, and `URAEDA_REPO`, another repository to
  open. Other hosts and origins get 403. The phone reaches it through `tailscale serve --bg 4310`.
  Pages update live within 2 seconds of a commit, reload when back in the foreground, target an
  iPhone 17's 402 px with 44 px touch targets, and have a System, Light, or Dark theme switch.
- ＋ on every page jots a line into a section of `PRIORITIES.md`, Next by default; the Priorities
  page moves lines by dragging or through a menu, edits and deletes them, each change written
  uncommitted, then committed alone as `chore: update the priorities` or discarded back to the
  committed file. Lines move with their nested items, and the rest of the file stays byte for byte.
- A save never overwrites a change made elsewhere: it carries the answer or the hash it started
  from, and a mismatch shows the new version, keeping the human's text; a field with nothing waiting
  to be saved takes a text changed elsewhere. Writes are serialized, one at a time. A hook's refusal
  keeps the files written, shows its whole output, and offers "Try again".
- Raw HTML in a file is shown as text; mockups open sandboxed in a new tab, with
  `Content-Security-Policy: sandbox`; links to code show the file's raw text, for tracked,
  non-hidden files only.

## Design

The core does the work, the server serves it, and the UI draws it. The core turns each workflow file
into a flat tree of blocks with source lines, recognising the skill's callouts, typed bullets, and
list callouts, and builds structured items on top (questions, options, stories, tasks, comments,
rulings, priorities). Its actions check, write, and commit themselves, through worktrees, so `ura`
and the binding share them. A core watcher reports which features and files changed. The server
exposes it all as fate sources, mutations, and live updates through a small adapter for data outside
a database; the UI never parses markdown and draws the blocks with Astryx, in a reading layout where
hierarchy comes from type, bands, and hairlines, never a box inside a box.

- Document tree and items:
  [`crates/core/src/files/document.rs`](/crates/core/src/files/document.rs),
  [`items.rs`](/crates/core/src/files/items.rs), and the parsers in
  [`crates/core/src/files/`](/crates/core/src/files/) (`clarifications.rs` with answer composing and
  splitting, `spec.rs`, `plan.rs`, `review.rs`, `rulings.rs`, `priorities.rs`).
- Worktrees and commits: [`place.rs`](/crates/core/src/actions/place.rs) `reach` finds or creates
  the worktree, never switching; [`git.rs`](/crates/core/src/git.rs) resolves a relative
  `core.hooksPath` against the main checkout; [`commit.rs`](/crates/core/src/actions/commit.rs)
  keeps a hook's whole output.
- Actions in [`crates/core/src/actions/`](/crates/core/src/actions/) (answer, review, draft, text,
  start, priorities), and [`api.rs`](/crates/core/src/api.rs), the entry points the binding calls,
  under one write lock.
- Workspace: [`workspace.rs`](/crates/core/src/workspace.rs) reads merged features, features from
  their worktrees, and drafts linked from priorities.
- Watcher: [`watch.rs`](/crates/core/src/watch.rs), on `notify` alone, reads the workspace again
  after 200 ms of quiet (ruling R1).
- Binding: [`crates/binding/src/lib.rs`](/crates/binding/src/lib.rs), async functions and
  `watch(repo, onChange)`, with generated declarations in [`packages/binding/`](/packages/binding/).
- Server: [`packages/server/src/`](/packages/server/src/), the fate adapter
  [`fate/source.ts`](/packages/server/src/fate/source.ts), mutations, live updates in
  [`live.ts`](/packages/server/src/live.ts), and the host and origin
  [`guard.ts`](/packages/server/src/guard.ts). Core refusals reach the UI as fate's `BAD_REQUEST`,
  prefixed `refused: `, `conflict: `, or `hook: ` (ruling R3); selections inside plain objects are
  answered with the whole object ([`fate/select.ts`](/packages/server/src/fate/select.ts), ruling
  R4).
- Web UI: [`packages/web/src/`](/packages/web/src/), the shell, home, feature, document, round,
  review, editor, and priorities pages, with [`Blocks.tsx`](/packages/web/src/Blocks.tsx) drawing
  the tree (callouts as a 4 px bar, not Astryx's `Banner`, ruling R5) and
  `@astryxdesign/theme-neutral` as the theme.
- Dev entry: [`vite.config.ts`](/vite.config.ts) mounts the Hono app in Vite's dev server, with
  [`.env.example`](/.env.example) documenting the settings. The layout check at 402 × 874 runs in
  WebKit, in [`layout.test.tsx`](/packages/web/src/__browser__/layout.test.tsx), counting text as
  cut only where an element clips it (ruling R6).

## Questions

### Round 01

#### Q1: Which human steps does the UI perform?

**Answer:** A: every human step, answers, spec, plan, and assessment reviews, priority lines, drafts
and proposals edited and committed, and starting a feature from a draft.

#### Q2: How does your iPhone reach the server?

**Answer:** A, "for the moment": `tailscale serve` to the server on 127.0.0.1, with the accepted
hosts "easy to set through env variables in a `.env` at the repo root".

#### Q3: Where does the UI write when a feature's branch is not checked out?

**Answer:** A: the checkout or worktree on the branch, else a worktree the server creates, "and we
actually should go further: `ura start` should create a worktree by default".

#### Q4: Where does the structure the UI draws come from?

**Answer:** A: the core turns each file into a tree of blocks with source lines, plus the structured
items, and React draws it with Astryx.

#### Q5: Does fate stay the data layer?

**Answer:** A: keep fate, with a source per type over the binding and live views from a watcher, and
drop the stack decision's fallback; "making a fate adapter is supposed to be pretty easy".

#### Q6: Do finished features show?

**Answer:** A: merged features in a Done group, and in `ura status`, noting that a coming "finish
feature" workflow may not keep all artifacts.

#### Q7: How are the screens organised?

**Answer:** A: home lists what waits on the human, then features by priority, plus the Now and Next
priorities "with the option to turn it into a draft or a draft into a proposal".

#### Q8: How is a round of questions answered?

**Answer:** A: every question on one page, follow-ups inside their parent, a progress bar, and the
settled points, notes, and Submit at the end.

#### Q9: What do you type drafts, proposals, answers, and comments in?

**Answer:** A: Astryx's text area, growing with its text, for everything.

#### Q10: Which repositories does the UI open now?

**Answer:** A: `vp dev` at Uraeda's root opens Uraeda, and an environment variable opens another
repository from Uraeda's checkout.

#### Q11: Which dependencies does the UI add?

**Answer:** A: `@astryxdesign/theme-neutral` only, pinned like Astryx.

#### Notes

The human approved the 16 points settled without them with "LGTM": among them, the actions' commits
move into the core, answers save as typed and Submit commits, review comments anchor to blocks, a
save never overwrites a change made elsewhere, and no raw HTML from a file is rendered.

## Decisions

- [Stack](../decisions/stack.md), changed: the server also accepts the host names in
  `URAEDA_ALLOWED_HOSTS`, fate's fallback rule is dropped, and the web UI draws the core's document
  tree and never parses markdown.
- [Git](../decisions/git.md), changed: tools never switch the checkout unless asked with a flag,
  write through worktrees at `.worktrees/<branch>/`, `ura start` creates one by default, relative
  hook paths resolve against the main checkout, and `.worktrees/` stays out of `git status`. This
  reverses Q7 of the [CLI core](../done/2026-10-10-cli-core.md), where `ura answer` switched the
  checkout.

## Changes after approval

- The watcher uses `notify` alone, with its own 200 ms quiet loop, not `notify-debouncer-full`
  (ruling R1).
- `ura check` problems show only for features read from a working tree; one read from its branch's
  tip shows its frontmatter's problems only (ruling R2).
- Callouts are drawn as a bar with a bold title, not Astryx's `Banner` (ruling R5).
- A feature and a bug sharing a folder name show as one, the first read, as `ura` does (ruling R8,
  raised by the pull request's review).
- Pull request fixes: writes are serialized; a verdict is refused when the file on disk differs from
  the committed version reviewed; raw files are served only when tracked and never hidden, so `.env`
  and `.git/` are not; a retried commit handles a review file already deleted; nested priority items
  render their text.
- Pull request fixes: answers, notes, and drafts stay in step with the files, take changes made
  elsewhere when nothing waits to be saved, and are saved before Submit; Submit, Commit, and Start
  stop when what is shown was not saved; drafts are read again when their page is shown.
- Pull request fixes: draft paths must be plain paths under `specs/drafts/` or `specs/backlog/`; a
  bug's files under `specs/bugs/` open, save, and commit; Discard restores the priorities from
  `HEAD`, staged edits included; drafting a line carries the priorities' hash.
- Pull request fixes: general review comments are editable, table rows are commentable, and the
  server keeps its watch for as long as it runs.
- Pull request fixes: `.env.example` and the README say to list the machine's full tailnet name,
  like `mac.tail1234.ts.net`, and reach it with `tailscale serve --bg 4310`, since the server
  listens on 127.0.0.1 only. CI and `nix develop` got what WebKit's layout tests need.

## Follow-ups

- A worktree deleted by hand without `git worktree prune` is skipped by the default branch's reads
  only once it is written to (`api.rs`).
- `vp dev` with the binding not built fails on the first request rather than at start (`dev.ts`).
- An answer with an unclosed code fence breaks the questions after it, as it would typed by hand
  (`clarifications.rs`).
- The skill's setup section does not repeat the worktrees, which its branches section covers.
- The UI computes which follow-ups show, and the answer shown while a save runs, from the core's
  `applies`, letters, and comment, rather than receiving them (`RoundPage.tsx`).
- Bugs could get their own `bugs/<folder>` id, if a feature and a bug ever share a folder name.
- Removing worktrees and branches of merged features was left to the "finish feature" workflow.
- Packaging the UI to run from any repository, like `ura web`, was left for a later feature.
