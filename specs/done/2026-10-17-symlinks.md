# Record: Share the main checkout's builds with new worktrees

> [!NOTE]
>
> The record of a merged change, not instructions to follow. Started on 2026-10-17, finished on
> 2026-10-17, in [its pull request](https://github.com/mrtolkien/uraeda/pull/28). Its full files are
> in git: `git log -- specs/changes/2026-10-17-symlinks/`.

## What and why

Every new worktree built its Rust code and reran its checks from scratch: each compiled every
dependency again, for 11 to 15 GB of `target/` each, and its first `vp run ready` replayed nothing.
The human asked to link the `node_modules` and Rust build folders, "and everything that makes
sense", into the worktrees, to save that CPU and storage.

## Behaviour

- The first dev shell (`nix develop`) in a linked worktree without `target/` clones the main
  checkout's `target/`, on a filesystem that clones files (btrfs, XFS, APFS), and says so on stderr.
  The worktree's first build compiles only the workspace's crates: `cargo nextest run --no-run`
  compiled 3 crates in 146 s of CPU, against 234 crates and 340 s from scratch.
- The clone never stands for the worktree's own code: the workspace's crates, their binaries and
  libraries, are always built again, whatever the files' times.
- On a filesystem without clones, nothing is copied, and the shell says why.
- Once the worktree's dependencies are installed, the next shell copies the main checkout's Vite
  Task cache, so `vp run ready` replays the checks whose inputs match the main checkout's.
- A worktree that has its own `target/` or task cache, the main checkout, and CI are left as they
  are. A seed that fails or is stopped midway leaves nothing `git status` shows.
- Nothing is linked, and `node_modules` stays installed per worktree.

## Design

Linking was ruled out: Cargo judges freshness by files' times, so with one `target/`, by a link or a
shared `build-dir`, a worktree whose files were older than another checkout's last build ran that
build's code, and its tests ran the other checkout's binary. pnpm already links `node_modules`'
files from its store, about 60 MB per worktree.

The dev shell's `shellHook` in [`flake.nix`](/flake.nix) runs
[`worktree-seed.ts`](/packages/server/scripts/worktree-seed.ts) when the checkout's `.git` is a file
and `target/` or the task cache is missing. `seedTarget` clones `target/` with
`cp -a --reflink=always` into `.target-seeding-<pid>/target/`, which `.gitignore`'s `target/` rule
hides, then `forgetPackages` removes the fingerprints of the packages `cargo metadata --no-deps`
lists, in every profile and target folder, with the files Cargo copied next to them, before the
clone is moved into place. `seedTaskCache` reads the cache's SQLite databases with `VACUUM INTO`,
then copies its archives. [`AGENTS.md`](/AGENTS.md) tells agents what the shell does.

## Changes after approval

- R4: `node_modules` is not linked, unlike the proposal's wording, since pnpm already shares its
  files and a shared folder would let a branch's install change the main checkout's.
- R1: `target/` is cloned once, not linked, unlike the proposal's wording, since a shared build ran
  stale code.

## Follow-ups

- Without clones, every shell retries the clone and prints its failure until Cargo creates `target/`
  (inbox, Deferred fixes).
- A lost race, or an empty task cache, is still reported as seeded (inbox, Deferred fixes).
- The shell hook assumes the current repository is Uraeda, and overwrites a `root` variable (inbox,
  Deferred fixes).
- The first shell blocks about 8 s while cloning, silently (inbox, Deferred fixes).
- The main checkout's task cache reads `.worktrees/` as inputs for `ts:check` and `specs:check`, so
  fewer of its entries hit in a worktree (inbox, Quickfixes).
- The clone does not wait for a build running in the main checkout: a dependency rebuilt during the
  clone can fail the worktree's first build, fixed by `cargo clean -p <crate>`.
