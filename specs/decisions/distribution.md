# Distribution

The web UI and its server ship as one npm package, `uraeda`, which users run with `npx uraeda` on
their own Node. The native binding comes in one small package per platform, which npm picks at
install time, the way napi-rs, Biome, and Rolldown ship. `ura` keeps its own installers, and both
are released from the same tag, with the same version.

## Rules

- The web UI and its server MUST ship as the npm package `uraeda`, whose `uraeda` command starts the
  server. It MUST require Node 24 or later, through its `engines` field, and MUST NOT bundle a Node
  runtime. Checked by the package's smoke test.
- The native binding MUST ship in one npm package per platform the [toolchain](toolchain.md)
  decision supports, named as napi-rs generates them: `uraeda-binding-linux-x64-gnu`,
  `uraeda-binding-linux-arm64-gnu`, `uraeda-binding-darwin-x64`, and `uraeda-binding-darwin-arm64`.
  `uraeda` MUST list them in `optionalDependencies`, with the exact version it is released with.
  Checked by the release workflow's gate.
- The packages MUST NOT run install scripts, and MUST NOT download anything when they run. Checked
  by review.
- `uraeda` MUST hold the server bundled into one JavaScript file, the built web UI, a copy of the
  skill as the agents' plugin, and the binding's loader generated by napi-rs, unchanged. Checked by
  the package's smoke test.
- The server MUST find its plugin, its web UI, and its checkout through one module, which knows the
  checkout's layout and the package's. No other module MAY build these paths. Checked by review, and
  by the module's tests.
- The server started from the package MUST NOT read a `.env` file: its settings come from its flags
  and its environment. Checked by the package's smoke test.
- The npm packages MUST be published by CI, from the version tag that releases `ura`, with the
  version of the Cargo workspace, through npm's trusted publishing. The repository MUST NOT hold an
  npm token. Checked by the release workflow, and by review.
- A release MUST publish the platform packages before `uraeda`, and only once the four binaries are
  built and the package's smoke test has passed on Linux x64 and macOS arm64. A release that stopped
  part way MUST be completed with the same version, never a new one. Checked by the release
  workflow.

## Why

The human chose the npm package over single executables built with Node or Bun, and over a desktop
app: it is 3.5 MB where the executables were 159 MB and 90 MB, it uses stable tooling, and the
server runs on the Node its tests run on
([Q1](../2026-10-14-run-ui/clarifications-01.md#q1-how-does-uraeda-ship),
[how the server ships](../2026-10-14-run-ui/discovery-01.md#how-the-server-ships),
[the spikes](../2026-10-14-run-ui/discovery-01.md#the-spikes)). `ura` stays separate, so the
[stack](stack.md) decision's CLI keeps needing no runtime
([Q2](../2026-10-14-run-ui/clarifications-01.md#q2-does-ura-start-the-web-ui)). The platform
packages take the names the generated loader already looks for
([Q3](../2026-10-14-run-ui/clarifications-01.md#q3-which-names-does-uraeda-take-on-npm)), and CI
publishes them without a stored secret
([Q6](../2026-10-14-run-ui/clarifications-01.md#q6-how-are-releases-published-to-npm)).

npm releases cannot be replaced, and are not atomic: a missing platform package breaks every user of
that platform, so the gate and the order come from napi-rs's own release guide
([napi-rs publishing](../2026-10-14-run-ui/discovery-01.md#napi-rs-publishing)). Install scripts are
skipped or restricted by `pnpm dlx`, and `optionalDependencies` are not
([npm and npx](../2026-10-14-run-ui/discovery-01.md#npm-and-npx)). Started by `npx` in a project, a
`.env` would come from that project, and a cloned repository could widen the host names the server
accepts ([a project's `.env`](../2026-10-14-run-ui/discovery-01.md#a-projects-env)).

## Alternatives considered

- A single executable built with Node's single executable applications: nothing to install, but 159
  MB, experimental tooling, and Node 26.
- A single executable built with Bun: 90 MB and proven by Claude Code, opencode, and Backlog.md, but
  users would run Bun while tests run on Node.
- An Electron desktop app: no browser tab, but signing, an updater, and the phone still needing the
  server.

## Consequences

- Users need Node 24 or later on their machine, and `claude` for sessions, as before.
- Each release publishes five packages, and each name needed one publish by hand before CI could
  publish it.
- A release that fails half way leaves some platforms broken until it is completed.
- Every later feature that adds a file the server reads at run time adds it to the paths module and
  to the package's contents.
- A single executable can still come later, published through the same packages, without changing
  the command users run.

## Applies to

- `packages/uraeda/`, [`packages/binding/`](/packages/binding/),
  [`packages/server/src/`](/packages/server/src/), [`.github/workflows/`](/.github/workflows/), and
  every feature that adds a file the server reads at run time, or changes how Uraeda is released

## Revisit when

Node's single executable applications leave active development, or users ask to run Uraeda without
installing Node.
